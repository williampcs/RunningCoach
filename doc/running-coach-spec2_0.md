## 1. 目標與範圍

### 1.1 為什麼要改 [已對齊]

v1.x 需要使用者自己架 VM、設定 Discord bot、申請兩組 API key，只有會寫程式的人能用。v2 要讓一般跑者開箱即用，同時不讓作者持有使用者的生理資料與金鑰。

### 1.2 目標 [已對齊]

- 一般使用者：打開網頁或 App 即可使用，不需要架任何東西。
- LLM 兩種管道，由使用者自選：
  - **BYOK**：自己填 LLM API key，key 只存在使用者裝置。
  - **訂閱**：付費使用作者的代理 server，不需要自己的 key。
- 活動資料兩種管道，由使用者自選：自填 Intervals.icu API key，或授權 App 取得資料（Intervals.icu OAuth／健康 App）。
- 透明：使用的模型、資料流向、server 會碰到哪些資料，全部明文揭露（見第 4 節）。
- 保持開源。想接 Discord 等第三方平台的人，可以拿 repo 自建。

### 1.3 不做的事 [提案]

- 作者不營運「託管版聊天 bot」。接 Discord／LINE 一律是自建。
- 作者的 server 不儲存對話、訓練資料、生理資料、使用者的 API key。
- 不做用模型判斷意圖的路由，也不做手機本地模型（理由見 6.3）。
- v2.0 不做跨裝置同步，只提供匯出／匯入。
- 自建的 Discord 外殼維持單人使用，不做多租戶。

## 2. 整體架構

### 2.1 架構圖 [提案]

```
            ┌───────────────── 使用者裝置 ─────────────────┐
            │  外殼（擇一）                                  │
            │   ├─ 網頁版 PWA                                │
            │   └─ 手機 App（網頁包裝 + 健康 App 橋接）       │
            │                                               │
            │  共用核心（TypeScript 函式庫）                  │
            │   agent 迴圈／五層記憶／工具／活動同步           │
            │                                               │
            │  本地 SQLite ・ 本地金鑰儲存                     │
            └───────┬──────────────────────┬───────────────┘
                    │ LLM 請求              │ 活動資料
        ┌───────────┴──────────┐           │
        │ BYOK：直連 LLM 供應商  │           ├─ Intervals.icu API
        │ 訂閱：經薄代理轉發     │           └─ 健康 App（僅手機 App）
        └──────────────────────┘

  自建路線：同一份共用核心 + Discord 外殼，跑在使用者自己的機器上（Node）
```

### 2.2 四個組成 [提案]

| 組成 | 內容 | 誰來跑 |
|------|------|--------|
| 共用核心 | agent 迴圈、記憶組合、對話壓縮、工具定義與執行、Intervals.icu 串接、SQL schema | 被下面三者引用 |
| 網頁／App 外殼 | 介面、本地儲存驅動、金鑰儲存、設定 | 使用者裝置 |
| Discord 外殼 | 訊息收發、slash 指令、訊息分段 | 自建者的機器 |
| 薄代理 | 訂閱驗證、額度控管、轉發 LLM 請求 | 作者（無狀態雲端服務） |

### 2.3 語言與框架 [已對齊]

- 共用核心、網頁、Discord 外殼、薄代理全部用 TypeScript，放在同一個 repo（npm workspaces）。
- 核心不拆成兩種語言。若核心留 Python、App 用別的語言，記憶邏輯會有兩份實作而逐漸不一致。
- 手機 App 以網頁包裝為主，只有讀取健康 App 的橋接使用原生程式碼。
- 網頁前端：React + Vite（第一版的選擇，介面還薄，要換框架的成本目前很低）。

### 2.4 repo 結構

| 路徑 | 內容 |

| `apps/discord` | 自建用的 Discord bot（discord.js） |

## 3. 共用核心

### 3.1 從 v1.4 沿用的部分 [提案]

行為以 v1.4 規格為準，移植時不改設計：

- 五層記憶架構（層 2、層 3 由工具按需載入）
- 對話壓縮與延續更新的摘要
- 13 個工具：`add_race`、`get_upcoming_races`、`update_race`、`cancel_race`、`update_race_result`、`update_athlete_profile`、`save_training_plan`、`get_training_plan`、`fetch_latest_activity`、`save_workout`、`save_pending_subjective`、`get_recent_workouts`、`get_pace_trend`
- 跑後回報的主客觀資料合併與同步延遲處理
- 分用途模型設定與累計用量統計
- SQLite schema 原樣沿用（含 `strava_id` 歷史欄位），另加 schema 版本號。v1 的資料庫檔可直接匯入。

### 3.2 核心對外的介面 [提案]

核心不直接碰平台，只透過以下介面，由各外殼提供實作：

| 介面 | 職責 | 網頁／App 實作 | Discord 外殼實作 |
|------|------|----------------|------------------|
| 儲存驅動 | 執行 SQL | 瀏覽器內的 SQLite | Node 的 SQLite |
| LLM 傳輸 | 送出一次模型請求 | 直連（BYOK）或經薄代理（訂閱） | 直連（BYOK） |
| 金鑰儲存 | 讀寫 API key | 裝置本地安全儲存 | 環境變數 |
| 活動來源 | 取得活動清單與明細 | Intervals.icu；App 另有健康 App | Intervals.icu |
| 時鐘／時區 | 目前時間、使用者時區 | 裝置時區 | 設定值 |

### 3.3 共用比例

v1.4 的邏輯除了 Discord 介面、進入點與設定之外，全部進了共用核心；兩個外殼都只跟 `Coach` 這個類別互動。網頁／App 的介面是全新工作，不在共用範圍內。

### 3.4 LLM 供應商 [已對齊]

核心的工具迴圈與供應商無關，各供應商以轉接層接上：

| 轉接層 | 涵蓋 | 實作方式 |
|--------|------|----------|
| Claude | Anthropic 直連、訂閱代理 | Anthropic 官方 SDK |
| OpenAI 相容 | OpenAI、Gemini 的相容端點、其他相容服務 | 直接呼叫 Chat Completions |

- Claude 有預設模型（主對話 Opus 5.5、跑後摘要 Haiku 5.5、對話壓縮 Sonnet 5.5，沿用 KI-020）。其他供應商的模型 ID 由使用者填寫，程式不內建，避免模型更名後過期。
- 訂閱代理只提供 Claude。
- OpenAI 相容轉接層只以模擬伺服器測過 request／response 的形狀，尚未對真實的 OpenAI 或 Gemini 驗證。

**費用估計**（2026-10-16）：用量頁尾在 token 數之後附上「約 US$…」，網頁版與 Discord 都有。
- 依每次 API 呼叫實際回報的 token 數，各自乘上單價：一般輸入、快取寫入、快取讀取、輸出（含思考 token）分開計價。主對話用了工具時，每一輪都算進去。Haiku 5.5 依單次請求的提示長度分級計價，所以每次呼叫分開計算。
- 單價表在 `packages/core/src/llm/pricing.ts`，取自 Anthropic 官方價格表（2026-10-16 查證）。只收錄 Claude API 直連可用的模型；模型 ID 要完全相同或只多一段日期後綴，未收錄的模型（其他供應商、未來的新版本）不顯示金額，寧可不估也不要估錯。官方改價時要更新這張表。
- 只算主對話模型。同一則回覆裡觸發的跑後摘要、背景的對話壓縮、從其他 AI 帶入的整理，用的是其他呼叫，沒有算進去。
- 訂閱模式的金額是 API 成本，由作者負擔，不是使用者要付的錢；代理上線時要決定是否對訂閱者顯示。
- 沒有計入：資料駐留（`inference_geo: "us"`，1.1 倍）、fast mode、1 小時快取的寫入價（目前都沒有使用）。之後加入網路搜尋時，要加上每次搜尋的費用（6.6）。


### 3.5 與 v1 的行為差異

移植後用同一份資料庫、同一組工具呼叫，逐項比對了 Python 版與 TypeScript 版的輸出。資料庫寫入結果、同步訊息、活動正規化、對話 context 完全相同；差異只有以下幾項：

| 項目 | v1 | v2 | 性質 |
|------|----|----|------|
| 數字格式 | `10.0km` | `10km` | 語言差異，無實質影響 |
| 心率區間 | 以浮點數相乘，邊界偶爾少 1（最大心率 180 時 Z2 上限為 125） | 以整數百分比計算（126） | 修正 v1 的錯誤 |
| 訓練紀錄缺心率 | 顯示 `None/Nonebpm` | 顯示 `?/?bpm` | 修正 v1 的錯誤 |
| 同一筆訓練有多筆摘要 | `get_recent_workouts` 會把該筆訓練列出多次 | 只列一次，附最新的摘要 | 修正 v1 的錯誤 |
| 讀取摘要與對話 | 兩次獨立讀取，背景壓縮剛好落在中間時會漏掉一段對話 | 單一原子讀取 | 修正 v1 的競態 |
| 背景壓縮 | 連續訊息可能同時觸發兩次壓縮 | 進行中不重複觸發 | 避免重複計費 |
| 時區 | 寫死 Asia/Taipei，「今天」依主機時區 | 設定值（網頁版預設為裝置時區），所有日期運算一致使用 | 新增 |
| 長訊息截斷 | 層5每一則都截成 600 字，連剛送出的訊息也是 | 最新 3 則（含剛送出的訊息）完整帶入；較早的才截斷，標記附 `message_id`，模型可用 `get_full_message` 讀取全文（KI-028） | 修正 v1 的問題 |
| 用量頁尾的分層估算 | 剛送出的訊息同時算在「層5對話」與「訊息」 | 層5不含剛送出的訊息，只算在「訊息」；實際的輸入、輸出、累計輸入不受影響 | 修正 v1 的錯誤 |
| 訊息的傳送時間 | 沒有帶入，跨日後模型把前幾天訊息裡的「明天」當成今天說的 | 選手的訊息開頭標上傳送時間與距今天數，例：`[2026-10-15（星期三）21:30，昨天]`；教練的回覆不標。壓縮的輸入帶日期，摘要寫實際日期（KI-030） | 修正 v1 的問題 |

## 4. 資料流與隱私

### 4.1 各模式下誰會碰到什麼 [已對齊原則，細節為提案]

| 資料 | BYOK | 訂閱 | 自建 Discord |
|------|------|------|--------------|
| 對話、訓練紀錄、生理資料的儲存位置 | 使用者裝置 | 使用者裝置 | 自建者的機器 |
| LLM API key | 使用者裝置 | 作者的代理持有作者的 key | 自建者的機器 |
| Intervals.icu key／token | 使用者裝置 | 使用者裝置 | 自建者的機器 |
| 送給 LLM 的內容是否經過作者 server | 否 | 是，僅在記憶體中轉發，不落地 | 否 |
| LLM 供應商是否看到內容 | 是 | 是 | 是 |
| 作者 server 儲存的資料 | 無 | 帳號識別、訂閱狀態、token 用量計數 | 無 |

### 4.2 揭露原則 [已對齊]

- App 內與隱私政策明列：使用的模型與供應商、每種模式的資料流向、代理儲存的欄位。
- LLM 供應商是否遵守其資料政策，作者無法保證，只能如實揭露其公開條款並提供 BYOK 作為替代。
- 首次使用訂閱模式、首次授權健康 App 時，各取得一次明確同意。

### 4.3 查證結果（2026-10-10）

**1. Intervals.icu API 可以從瀏覽器直接呼叫。**
實測預檢請求：`access-control-allow-origin` 會回傳請求的來源，允許的標頭包含 `authorization`。網頁版的活動資料不需要經過任何轉發端點，4.1 的隱私表不用改。網頁版也已用模擬服務實際跑過這條路徑。Anthropic、OpenAI、Gemini 的 API 同樣允許瀏覽器直接呼叫（實測預檢通過）。

**2. Intervals.icu OAuth 需要 server 持有 client secret。**
依官方論壇的 OAuth 說明：

- 換 token 時必須以表單送出 `client_id` 與 `client_secret`，文件沒有提到 PKCE 或免 secret 的流程；有開發者為此另外架了一個小型 server 保管 secret。
- 沒有 refresh token，只有 access token；重新授權會讓舊 token 失效。
- 應用要先申請並經核准，核准前無法走 OAuth 流程。個人使用官方建議直接用 API key。
- 結論：「授權 App」這條路的換 token 步驟一定會經過作者的 server（可以放在薄代理上）。server 會在那一瞬間經手 token，換完交給 App 後不保存。隱私說明要如實寫出這一點；「完全不經過作者」只有自填 API key 做得到。
- 這份文件的主文年代較早，申請前要再向 Intervals.icu 確認現況。

**3. 上架審查條款。**

- Apple 5.1.2(i)（2025-11 起）：把個人資料分享給第三方 AI 之前，要在 App 內明確揭露並取得使用者同意，寫在服務條款裡不算。已有健身 App 因審查員沒看到同意畫面而被退件。
- Apple 5.1.3：健康資料不得用於廣告或資料探勘、不得存放在 iCloud；使用 HealthKit 的 App 主要用途必須是健康與健身服務。
- Google Play：所有 App 都要填寫健康類 App 聲明；使用 Health Connect 的每一項權限要對應到使用者看得到的功能並說明理由；隱私政策要寫明資料分享給哪些第三方。沒有找到專門針對第三方 AI 的條款。
- 對設計的影響：4.2 的「首次使用時取得明確同意」不是可有可無，必須是 App 內的獨立畫面。網頁版的設定頁已照這個方向做（依模式與供應商分別顯示資料流向並要求勾選）。
- 以上來自二手整理與開發者論壇，送審前要對照當時的官方條文。

**4. 個資法規。**

- 台灣：依國發會 107 年的函釋，民眾自行測量、直接交給業者的生理數據，若沒有醫事人員參與診察或治療，不屬於個資法第 6 條的特種個資，但仍是一般個資，適用第 19、20 條（蒐集要有特定目的與同意等）。該函釋不是針對運動數據，適用到本專案是推論。
- 歐盟：心率等資料在能反映健康狀態時會被視為 GDPR 的健康資料（特種個資），消費型 App 通常需要「明確同意」，不能以正當利益為依據。若不打算服務歐盟使用者，要在上架地區與條款上排除。
- 這兩點都需要法律專業確認，本文不構成法律意見。

## 5. 薄代理

### 5.1 行為 [提案]

- 對外介面與 LLM 供應商的訊息 API 相容，客戶端只需切換網址與憑證。
- 每次請求：驗證訂閱 → 檢查額度 → 轉發（含串流）→ 累計用量。
- 無資料庫存放請求或回應內容；日誌不記錄內容。

### 5.2 防濫用 [已對齊方向，細節為提案]

客戶端開源，訂閱者可以把代理拿去做與跑步無關的事。以上限控制損失，不嘗試判斷內容：

- 模型白名單
- 單次輸出 token 上限
- 每月 token 預算
- 請求頻率限制

### 5.3 實作現況

- 端點：`POST /v1/messages`（轉發，含串流）、`GET /v1/usage`（訂閱者查自己本月用量與額度）、`/admin/accounts…`（建立帳號、停用、調整預算、重發憑證）。
- 訂閱者以代理發給的憑證取代 API key，其餘與直連 Anthropic 相同。代理只存憑證的雜湊。
- 額度以金額計：依各模型的每百萬 token 價格換算，累計到每月預算為止。預設政策（可用模型、價格、單次上限、每月預算、每分鐘請求數）寫在 `apps/proxy/src/policy.ts`，可用環境變數覆寫。**預設的價格與每月 3 美元預算只是佔位，上線前要依現行價目與定價調整。**
- 只轉發白名單內的請求欄位；加價功能（`speed`、伺服器端工具等）與 beta 標頭一律拒絕或丟棄。
- 管理端點是帳號與金流服務的接點：金流服務（不在本 repo）收到付款後呼叫它建立或停用帳號，代理本身不知道誰付了錢。
- 每分鐘請求數目前以單一執行個體的記憶體計數，多個體部署時要改用平台的限流機制。
- 串流被下游提早中斷時，輸出 token 只算到最後一個已送達的用量事件，會少計。

### 5.4 待決定

- 帳號與登入方式（訂閱者如何取得憑證）。
- 金流：網頁版可用一般線上金流；App 內訂閱須走商店內購。
- 定價與每月額度。
- 部署平台。Node 進入點已實測；Cloudflare Workers 進入點（用量存 D1）只通過型別檢查，尚未實際部署。

## 6. 網頁／App 外殼

### 6.1 第一版範圍

- 形式：網頁版。已有安裝用的 manifest，但還沒有 service worker，離線無法開啟。圖示的原圖是 `apps/web/public/icon-512.png`（使用者提供，2026-10-15），分頁用的 32px、192px 與 iOS 主畫面用的 180px（四角填上底色）由它縮小產生。
- LLM：BYOK（Claude、OpenAI、Gemini、其他相容服務）與訂閱代理兩種模式都接上了。
- 活動來源：僅 Intervals.icu（自填 API key）。
- 功能：對話、選手資料、賽事管理、訓練計畫檢視與手動編輯、跑後回報、手動同步、用量與記憶狀態檢視、資料匯出／匯入（可匯入 v1 的 `coach.db`）、從其他 AI 服務帶入選手資料（6.5）、每日自評與恢復資料、教練動態（6.7）。
- 儲存：資料庫在瀏覽器的 OPFS；金鑰與設定在 localStorage（預設為明文，可以啟用密碼鎖加密 API key，見下方）。同一個網站同時只能開一個分頁，第二個分頁會退回暫時性的記憶體資料庫並顯示警告。
- 對話回覆逐字串流：模型思考時顯示「教練思考中…」，執行工具時顯示正在做的事（例如「讀取最新的跑步活動…」），文字一產生就逐段顯示。完成後才寫入對話紀錄，中途失敗不保留半段回覆。
- 思考階段只顯示「思考中」，不顯示思考摘要（2026-10-11 決定）。新模型預設不回傳思考內容，要顯示摘要得另外在請求中要求。
- 新手引導（2026-10-15，依手機試用的回饋）：對話頁在設定未完成時顯示「開始使用」卡片，依序引導設定 AI 模型、從 Intervals.icu 取得 API key 並填入、同步最近 14 天、填寫選手資料；必要的三步完成後自動隱藏，也可以略過。設定頁的 Intervals.icu 區塊列出取得 key 的步驟與連結，儲存後若還沒有訓練紀錄，提示「下一步：同步最近 14 天」並可直接同步。
- 補填體感：跑後回報的表單只處理今天的跑步；同步進來、當時沒有回報的紀錄，可以在下方的訓練列表按「補填體感」（已有的顯示「修改體感」），存檔後帶著體感重新產生分析，並可請教練針對那一次給回饋（`Coach.addSubjective()`）。對話與 Discord 目前沒有對應的工具，無法用說的補填。
- 跑後回報頁的 AI 摘要以 Markdown 顯示（原本是純文字，會露出 `**` 等符號）。
- 設定頁的「重置」：「清除資料，保留設定與 API key」清空資料庫的每個資料表（保留結構，於資料庫執行緒的單一請求內完成，進行中的查詢不會撞上資料表不存在）；「全部重置」連設定一起清除，回到第一次使用的狀態。兩者都會讓新手引導重新出現。
- API key 的保護（2026-10-15，[KI-027](known-issues.md)）：設定頁的「保護 API key」列出降低風險的做法（專用的 key、在供應商後台設金額上限、外洩時撤銷重產），並提供選用的密碼鎖。密碼經 PBKDF2-SHA256（60 萬次）產生 AES-GCM 金鑰，加密 LLM 的 API key、代理憑證與 Intervals.icu 的 key，其餘設定維持明文。啟用後每次開啟頁面先輸入密碼，解鎖前不開啟資料庫；金鑰只放在記憶體，不可匯出。忘記密碼只能刪除加密的 key 重新填寫，資料與其他設定保留。對話與訓練紀錄不加密。
- 內容安全政策（CSP）：建置結果以 `<meta>` 限制只執行本站的腳本、圖片只從本站載入；開發伺服器的熱更新需要行內腳本，所以不加。連線對象開放所有 http(s)，因為「其他相容服務」的網址由使用者填寫。Markdown 不顯示圖片，避免模型回覆透過外部圖片的網址把資料帶出去。
- 測試模式（2026-10-16）：用假的跑步紀錄測試教練在各種情況下的反應，在設定頁啟用。
  - 使用另一個資料庫檔案（OPFS 的 `/coach-test.db`），正式的對話與訓練紀錄不受影響；停用後回到正式資料，測試資料保留到下次啟用。
  - 活動來源換成假資料，完全不連線 Intervals.icu；App 本來就只讀取 Intervals.icu，不會寫入，所以也不會汙染那裡的資料。LLM 照常使用使用者的設定，會正常計費。
  - 產生一段期間的紀錄：情境有穩定訓練、逐步加量、過度訓練跡象、受傷中斷後復出、賽前減量、不規律與資料缺漏；可以調整週數、每週次數、輕鬆跑配速、最大心率與亂數種子，同一組設定每次產生相同的資料（`packages/core/src/fake-activities.ts`，單元測試也用它）。最近 14 天的紀錄經一般的同步流程帶入，更早的直接存入、不產生 AI 分析；可以同時填入範例選手資料與一場賽事。
  - 新增單筆：日期、距離、時間、心率、爬升，可以用來測跑後回報。
  - 模擬今天的日期：之後日期的假資料會陸續出現，賽事倒數跟著變。
  - 畫面最上方一直顯示測試模式的提示；測試模式中的重置只清除測試資料庫，不提供「全部重置」，避免連帶清掉設定。
- 版面：以手機為主，分頁在底部。視窗寬度 900px 以上（桌面）分頁改為左側欄、內容放寬到約 850px，對話泡泡最寬 75%（2026-10-15，「能用就行」的簡單調整）。
- Discord 外殼不串流：Discord 只能反覆編輯同一則訊息，還有頻率限制，維持完成後一次送出。

### 6.2 與 Discord 版的行為差異 [提案]

Discord 沒有表單，所有讀寫都得經過工具呼叫。網頁版有介面後：

- 選手資料、賽事的新增修改由表單直接寫入本地資料庫，不經過模型。
- 活動由 App 直接拉取。跑後分析改為「帶著活動數據與體感的一次模型呼叫」，不再走工具迴圈。
- 工具仍保留在核心，供自由對話與 Discord 外殼使用。

### 6.3 模型路由 [提案]

由介面入口決定任務類型與模型（跑後分析、對話壓縮、自由對話各自對應固定模型），不另外用模型判斷意圖。自由對話固定走中階模型。

### 6.5 從其他 AI 服務帶入選手資料

使用者已在 ChatGPT、Claude、Gemini 等服務累積大量跑步相關的對話時，讓教練不必從頭認識他：讀取他提供的內容，填好選手資料、賽事與課表的建議值，使用者確認後才寫入，降低轉過來的成本。

**第一階段（2026-10-15 實作）：請原本的 AI 整理**

1. 選手資料頁的「從其他 AI 帶入」顯示一段提示詞（`IMPORT_PROMPT`），使用者複製到原本的服務送出。提示詞要求依固定格式整理目標、PB、生理資料、訓練偏好、未來賽事與每週課表，不確定的寫「不明」，不提供姓名與聯絡方式。
2. 使用者把回覆貼回來（也可以貼與真人教練或跑友的對話），按「整理」。摘要用的模型擷取成 JSON（`Coach.extractImport()`）；程式只保留認得的欄位，丟掉「不明」、空值、已過去或日期不明的賽事。
3. 確認畫面逐項列出建議值，每一項都可以修改、取消勾選。目前空白的欄位預設勾選；與目前不同的值預設不勾選，並顯示目前的值；與目前相同的不列出。已有同一天賽事的預設不勾選。已有本週計畫時，課表預設不勾選並提示會取代。
4. 「帶入」只寫入勾選的項目（`Coach.applyImport()`）：選手資料、賽事，以及設為本週課表。原文只在畫面的狀態裡，不寫入資料庫或 localStorage，也不進對話紀錄；帶入、取消或離開這頁之後就丟掉。

決定（2026-10-15，使用者）：
- 只帶入「計畫與賽事」「選手資料」已有的欄位，不另外保存背景摘要；原文用完即丟。
- 以確認畫面取代「在對話中跟使用者確認」：貼進對話的原文會存進對話紀錄，並在壓縮前隨每則訊息重送給模型，無法做到用完即丟。
- 內容只送到使用者設定的 LLM，與一般對話的資料流向相同。訂閱模式會經過代理並由作者付費，屆時要限制長度。

**之後的階段（未排定）**

- 官方匯出檔：ChatGPT 與 Claude 的「匯出資料」都是含 `conversations.json` 的壓縮檔，Gemini 經 Google Takeout。檔案可能很大，要在瀏覽器的 Web Worker 解析，以關鍵字篩出相關的對話，分段交給摘要模型擷取，執行前顯示估計的 token 數與費用。各家格式會變動，每家都要有自己的解析器與測試。
- 分享連結：不建議。瀏覽器的跨來源限制讓網頁版無法直接讀取，得經伺服器抓取；分享頁由前端程式產生、格式隨時會變，也可能違反服務條款。
- Discord 外殼沒有對應的功能。

### 6.6 教練上網搜尋 [提案]

2026-10-15 討論，尚未決定。用在訓練資料以外、會變動的資訊：推薦裝備與補給品，查賽事資訊（日期、報名、路線、關門時間、接近比賽時的天氣）。

各供應商的支援（2026-10-15 查證）：

- **Claude**：API 內建 web search 伺服器工具，由 Anthropic 執行搜尋，回覆附引用來源。費用為每 1,000 次搜尋 10 美元，另外搜尋結果算進輸入 token（一次搜尋常有數千 token）。可以用 `max_uses` 限制每則訊息的搜尋次數，`user_location` 讓結果在地化，`allowed_domains`／`blocked_domains` 限制網域。預設啟用，組織管理員可以在 Console 關閉。另有 web fetch 工具，只能讀取對話中出現過的網址，例如使用者貼上的賽事頁面。
- **OpenAI**：Chat Completions 只有專門的搜尋模型能搜尋，而且每次都會搜尋；要讓模型自己決定何時搜尋，得改走 Responses API。現在的轉接層走 Chat Completions。
- **Gemini**：Google 搜尋的 grounding 只在原生 API，OpenAI 相容介面不支援。
- **其他相容服務**：沒有。

建議做法，第一階段只支援 Claude（含訂閱模式）：

- 設定頁加上開關「允許教練上網搜尋」，預設關閉；每則訊息最多搜尋 3 次；由使用者的時區推出 `user_location`。
- 轉接層：工具列表加上 web search，處理 `pause_turn`（把暫停的回覆原樣送回繼續）。現在的轉接層在工具往返時已把回覆的內容區塊原樣送回，搜尋結果的 `encrypted_content` 會保留。
- 介面：搜尋時顯示「搜尋網路中…」與查詢字詞，回覆下方列出來源連結；Anthropic 要求把搜尋結果呈現給使用者時附上原始來源。存進對話紀錄的回覆附上來源清單；搜尋結果本身不保存，之後的對話不會重送，也不會再為這些 token 付費。
- 用量：token 用量的頁尾加上搜尋次數。
- 安全：網頁內容不可信，可能夾帶指示（prompt injection）。同一回合搜尋過後，寫入類的工具（選手資料、賽事、課表、訓練紀錄）一律不執行，改請使用者在下一則訊息確認。Markdown 已不顯示圖片（6.1），用圖片網址把資料帶出去的管道已關閉。系統提示要求裝備推薦註明可能有業配並列出多個來源，賽事資訊註明來源與查詢日期。
- 資料流向說明加上：搜尋的查詢字詞由模型產生，經 Anthropic 送到它的搜尋服務；查詢不應包含個人資料。
- Discord 外殼共用核心，用 Claude 時一樣可用，來源以連結列出。
- **成本量測**（2026-10-16）：`tools/measure-web-search.ts` 用真實的 Claude API，以教練實際的系統提示與工具（選手資料是假資料）跑四個情境：不需搜尋的對照組、競速鞋推薦、能量膠補給、賽事資訊。每個情境比較三種模式：不搜尋、基本搜尋（`web_search_20250305`）、動態過濾（`web_search_20260318`）。報告列出每次的呼叫數、搜尋次數、token、金額，以及回覆、搜尋字詞與引用來源，寫到不進版控的 `data/measurements/`。需要真實的 key，在本機執行：`ANTHROPIC_API_KEY=… npx tsx tools/measure-web-search.ts`，可用 `--model`、`--scenarios`、`--modes`、`--max-uses`、`--repeat` 調整。已用模擬服務確認流程（含工具迴圈）與金額計算，還沒有真實的量測結果。
- 成本的特性：一則回覆裡搜尋了幾次，後續每一步都會重讀先前的搜尋結果，所以多次搜尋的成本比線性增加還快；搜尋後若還要呼叫教練的工具，結果會隨對話再送一次。可以壓低成本的做法：限制搜尋次數、動態過濾、搜尋時改用較便宜的模型、限制網域，以及 Prompt Caching。
- 之後要支援其他供應商，有兩條路：OpenAI 改走 Responses API、Gemini 走原生 API；或在代理上接搜尋 API（Brave、Tavily 等）作為一般工具。後者因瀏覽器的跨來源限制必須經過代理，也多一把 key 與一筆費用。

### 6.7 恢復資料、每日自評與教練動態（2026-10-16）

使用者決定先做 12.3 的「恢復資料」與「主動提醒」。使用者也指出手錶的恢復數據常和自己的感受不一致，所以同時收集選手的自評，兩者不一致時以自評為主（[KI-029](known-issues.md)）。

**資料**
- 恢復資料：同步時一併讀取 Intervals.icu 最近 14 天的 wellness（`GET /api/v1/athlete/{id}/wellness?oldest=…&newest=…`），存進 `wellness` 資料表：靜息心率、HRV（rMSSD）、睡眠時間、睡眠分數、準備度。同一天以新資料覆蓋，因為手錶的睡眠與 HRV 常在當天稍晚才補齊。只讀取，不寫回。沒有新的跑步也會更新；讀取失敗不影響跑步紀錄的同步，訊息附註「恢復資料暫時無法取得」。欄位名稱依搜尋到的文件，還沒有以真實帳號確認（9.4 第 1 項）。
- 每日自評：精神、痠痛、睡眠各 1–5 分，加上備註，一天一筆，存進 `daily_checkins`；同一天再記錄會覆蓋。可以在教練動態填寫，也可以在對話（含 Discord）直接說，由教練用 `save_daily_checkin` 記錄。
- 資料庫的 schema 版本升為 2，新增上面兩個資料表。舊的資料庫在開啟時自動建立；v1 不讀這兩個表，回退到 v1 仍可使用同一個檔案（9.2）。匯出、匯入與清除資料都涵蓋它們。

**判讀**（`packages/core/src/recovery.ts`）：用固定、可解釋的規則，不用模型判斷，也不換算成分數。
- 拿最近一天（今天或昨天）的手錶數據和「平常」比，也就是 8～35 天前的平均，至少要有 7 天的資料；資料不夠時改和前 7 天比（至少 3 天）。不和前幾天比，是因為過度訓練這類持續好幾天的偏差，會把前幾天的平均一起拉高。
- 手錶偏差：靜息心率高 5 bpm 以上、HRV 低 15% 以上、睡眠不到 6 小時或比平常少 1 小時以上。自評偏差：精神 2 分以下、痠痛 4 分以上、睡眠 2 分以下。
- 不一致時以自評為主：自評差而手錶正常，降低當天的強度；手錶偏差而自評不錯（精神 4 分以上），可以照計畫，但提醒留意。不用手錶的數據否定選手的感受。
- 教練看到的內容：有資料時，系統提示加上「今日身體狀況」（自評、手錶數據與平常的比較、判讀原則），沒有資料時不加。工具 `get_recovery_status` 列出最近幾天每天的手錶數據與自評，附上今天的判讀。跑後分析的提示帶入跑步當天的身體狀況；沒有資料時，提示和原本相同。

**教練動態**（`packages/core/src/feed.ts`、`apps/web/src/views/CoachFeed.tsx`）
- 12.3「主動提醒」的第一步：對話頁上方列出教練主動提醒的事項，打開 App 就看得到。內容由規則從本機的資料組出，不呼叫模型，也不花費用。之後的推播或 Discord 訊息只負責「按門鈴」，內容和這裡相同。
- 項目，警示排在前面：
  - 今天還沒自評：「今天身體感覺如何？」。手錶有偏差時一併提到，但說明手錶不一定準，請選手先說自己的感覺。
  - 自評之後：狀況差時建議降低強度，可以直接問教練怎麼調整；手錶偏差但自評不錯時，說明以選手的感受為主；都正常時只顯示已記錄。
  - 今天或昨天的跑步還沒回報體感；有等待同步的跑後回報。
  - 30 天內的賽事倒數，7 天內改為警示，可以請教練安排賽前幾天；已過去、還沒記錄成績的賽事。
  - 本週課表中今天的那一行。依「週一」「星期一」「禮拜一」等字樣比對；課表是 Markdown，比對不到就不顯示。
  - 跑量暴增：近 7 天比前三週的平均多 30% 以上，而且前三週平均至少 10 km。
  - 5 天以上沒跑。
- 每一項有對應的按鈕：回報身體狀況、前往跑後回報、同步、查看計畫、問教練。「問教練」會帶著問題開始一段對話。「知道了」隱藏該項，「收起」縮成一行；兩者只記當天（localStorage），隔天重新顯示，測試模式的模擬日期也適用。
- Discord 外殼沒有教練動態；自評與恢復資料的工具在 Discord 一樣可以用。

**測試資料**：測試模式的假資料也產生恢復資料，並依情境變化，例如過度訓練時最後 10 天靜息心率偏高、HRV 偏低、睡眠變少，減量時回升，可以用來測教練動態與教練的判讀。模擬服務的 Intervals.icu 也回傳 14 天的恢復資料，其中最後兩天偏差。

## 12. 產品方向討論（2026-10-16）

使用者問：對業餘跑者還缺什麼、可以往哪裡走；朋友在做社交平台，能否結合。以下是討論的結論，尚未排入開發。

### 12.1 對業餘跑者的欠缺，依影響排序

1. **門檻**：現在要自己申請 Intervals.icu 帳號、API key 與 LLM 的 API key，一般跑者大多做不到。對應：訂閱模式（不必自備 LLM key，5.4）、Intervals.icu OAuth（11 #10），長期是直接接手錶或健康 App（6.4）。各平台的 API 條款對 AI 使用的限制要先查證。
2. **課表沒有結構**：訓練計畫是一段 Markdown，無法對照「計畫 vs 實際」，也不能推到手錶。Intervals.icu 的行事曆可以放結構化的課表並同步到 Garmin 等手錶；把教練排的課表寫進去，跑者就能在手錶上照著跑，賽後也能比對完成度。
3. **教練不會主動找人**：現在只有使用者開口才回應。業餘跑者最需要的是提醒與追問：週計畫、賽前倒數、跑完沒回報時追問、連續缺課時調整。網頁版的資料只在裝置上，要做推播得有 service worker 與一個只送通知、不碰資料的伺服器；Discord 外殼已經有常駐的伺服器，可以先在那裡做。
4. **看不到進步**：沒有圖表。週跑量、心率對配速的趨勢、Intervals.icu 算好的體能與疲勞（CTL／ATL）都已有資料可畫。
5. **恢復資料沒用上**：Intervals.icu 也有 HRV、睡眠、靜息心率等 wellness 資料，可以讓「今天該不該練」的建議更有根據。2026-10-16 已做，並加上選手的自評（6.7）。
6. **換裝置**：資料只在一台裝置上，換機或多裝置都不方便（11 #8 的加密雲端備份）。
7. **建議品質沒有驗證**：沒有一組情境題由懂訓練的人檢查教練的回答，改提示詞或換模型時無法確認有沒有變差。

### 12.2 與社交平台結合

核心與外殼是分開的，Discord 外殼就是先例，接到另一個平台在架構上可行。依結合程度：

1. **分享卡片（最輕）**：把一次跑步的數據與教練的評語做成圖片或文字，使用者自己決定要不要貼。不需要對方的 API，也不涉及資料授權，可以先用來測試大家有沒有興趣。
2. **帳號連結與發文**：以對方的帳號登入，或代使用者把成果發到對方平台；從對方平台帶入揪團、賽事報名等資訊。
3. **教練進到社群裡（最深）**：像 Discord 外殼一樣，在對方平台做一個外殼，教練在私訊或群組裡回應；也可以做群組挑戰、群組的週報。

要注意的地方：
- 網頁版是資料留在裝置上的設計；教練進到社群裡，資料就得放在伺服器上（如同 Discord 外殼），要重新處理同意、保存與刪除。
- 心率等健康相關資料在個資法上可能屬於需要特別保護的資料，群組中的分享要逐項取得同意，預設不公開。
- 費用：群組裡人人都能呼叫教練時，LLM 費用由誰付要先講好。

要先問朋友的事：平台的性質與使用者（是否以運動為主）、有沒有機器人或 webhook 的 API、帳號系統、資料放在哪裡、怎麼營利。建議先做分享卡片，看反應再決定要不要做外殼。

### 12.3 第二輪討論與查證（2026-10-16）

雲端 session 的網路政策擋下 intervals.icu，以下查證來自搜尋引擎找到的官方頁面摘要、論壇與第三方文件，實作前要在本機以真實帳號確認。

**Intervals.icu OAuth**：有。官方的 Open API 頁面寫明支援 OAuth 2.0 與細分的權限（ACTIVITY、WELLNESS、CALENDAR，各有 READ／WRITE）。
- 要寄信申請：應用名稱、說明、網站、標誌、隱私政策網址、回呼網址。所以要先有隱私說明頁（9.4 第 13 項）。
- 換 token 要用 client secret，而且要在 2 分鐘內完成，靜態網頁放不了 secret，得經代理（11 #10 原本就預期代理要多一個端點）。
- 第三方文件說 token 不會過期、沒有 refresh token，論壇也有人回報幾小時後被拒；要實測。
- OAuth 只省掉「貼 API key」這一步，使用者仍然要有 Intervals.icu 帳號，並在那裡連上自己的手錶。

**課表推到手錶**：路徑是「教練 → Intervals.icu 行事曆 → 手錶」。
- 寫入：以 API 建立 `category: WORKOUT` 的事件，`description` 用 Intervals.icu 的課表語法（例如 `Warmup`、`- 10m Z2 Pace`、`Main Set 5x`、`- 1km 4:30/km Pace`）；需要 CALENDAR 的寫入權限。語法沒有正式規格，要從範例與官方的課表編輯器輸出歸納。
- 送到手錶：使用者在 Intervals.icu 的連線設定勾選「Upload planned workouts」。Garmin 會上傳大約一週的課表，改了會跟著更新；Suunto 經 SuuntoPlus Guides；COROS 有支援，但一次上傳 7 天的計畫，論壇回報上傳後在 COROS 端無法刪改、偶爾不同步；Wahoo 有回報無法顯示。Apple Watch 沒有走這條路，之後的 iOS App 可以用 Apple 的 WorkoutKit 直接排課表。
- 所以不只 Garmin，但各家品質不一，Garmin 最穩。

**主動提醒，不要因為通道而割裂**：教練主動的內容（今日課表、賽前倒數、跑完沒回報的追問）統一放在 App 裡的「教練動態」，每個通道只負責「按門鈴」，內容都一樣。
- 不靠任何通道也成立：打開 App 時，教練先列出待辦與提醒。所有外殼都一樣，先做這個。2026-10-16 在網頁版做了第一版（6.7）。
- 門鈴依通道而定：原生 App 可以在裝置上排定本地通知，不需要伺服器；網頁版的 Web Push 在 Android、桌面與 iOS 16.4 以後（加到主畫面）都可用，要一個只存推播訂閱與時間、不碰訓練資料的伺服器，推播內容只寫「教練有新訊息」，打開後在裝置上組出內容；Discord 與 LINE 可以直接發訊息。
- 不用自己建的被動提醒：課表寫進 Intervals.icu 後，手錶上就有今日課表；也可以輸出行事曆訂閱（.ics），由行事曆提醒。
- 需要伺服器的部分：新的跑步紀錄出現時立刻追問。手機 App 的背景執行受限，要即時就得有伺服器接收通知。

**用養成遊戲取代進步圖表**（使用者的構想，類似 Pikmin Bloom，但偏 RPG）：圖表對減量或休息的人容易帶來挫折，把運動抽象成角色的成長比較友善，也比較沒有個資疑慮，適合跟朋友的社交平台結合。設計原則：
- 獎勵持續與照計畫執行，不獎勵速度：完成課表、跑後回報、照計畫休息都算數；經驗值不會倒扣。
- 休息與受傷有正面的對應：休息是回復，受傷時給「養傷任務」（伸展、回報狀況），不是懲罰。
- 訓練週期對應遊戲的章節，比賽是關卡，不論成績都有完賽的慶祝。
- 收集要素用粗略的分類（晨跑、夜跑、雨天、長跑），不用 GPS 位置。

為了從一開始就保留相容性：
- 核心只對外提供一份抽象的「進度事件」（例如 `run_completed`、`planned_session_completed`、`rest_day`、`checkin`、`race_finished`），只帶日期與粗略的等級（強度、時長分級、連續天數），不帶心率、配速、位置等原始數字。
- 事件的 id 由來源紀錄穩定產生，重算不會重複計分；格式有版本號。
- 遊戲規則是事件紀錄的純函式，規則改了可以重算，不會失去歷史。
- 原始資料留在裝置上；只有進度事件可以在使用者同意後送到遊戲或社交平台。

**恢復資料**：可以做。Intervals.icu 的 wellness 資料（靜息心率、HRV、睡眠、主觀疲勞等），用 WELLNESS 的讀取權限；做成教練的工具，並在跑後分析中帶入。2026-10-16 已做，加上每日自評，不一致時以自評為主（6.7、KI-029）。

**跨裝置，不依賴雲端**：
- 一次性的搬家已經可行而且成熟：現在的匯出／匯入加上 AirDrop、附近分享；可以再加上掃 QR code、兩台裝置以 WebRTC 直接傳送。WebRTC 需要一個小伺服器交換連線資訊（不經手資料，傳輸本身加密），網路環境不好時要經中繼轉送加密後的流量。
- 持續同步但不經任何伺服器，在瀏覽器上還不成熟：兩台裝置要同時在線，連線也常受網路環境限制。我們的資料大多是只增不改（訓練紀錄、對話），加上少量會改的（選手資料、賽事、課表），自己做「每筆紀錄帶更新時間、後寫入者為準、刪除留標記」的同步就夠，不一定要引入 CRDT。
- 退一步的選項：放在使用者自己的雲端（Google Drive 的應用程式資料夾、iCloud），或經代理存放加密後的檔案，伺服器看不到內容。密碼鎖現有的加密（6.1）可以沿用來加密備份。

**建議品質靠使用者回饋個人化**：
- 每則回覆可以按讚／倒讚並寫一句原因，存在裝置上。
- 累積到一定數量時，請摘要模型整理成一段「教練風格偏好」（例如先講結論、少說教、多給數字），放進系統提示；選手資料頁可以看到並修改。使用者也可以直接說「以後回答短一點」，由教練用工具更新。
- 偏好只影響風格與重點，不能蓋過安全原則（例如疼痛、受傷的警訊）。
- 要改善所有人共用的提示詞，必須使用者自己選擇匿名分享回饋才收集。

### 12.4 環境的切分（2026-10-16 討論）

**現況**：
- dev：本機與雲端 session，用模擬服務開發（9.3）；網頁版另有測試模式（6.1），可以在正式網站上用假資料測試。
- prod：`main`。合併後網頁版發布到 GitHub Pages，Discord bot 部署到 VM。
- 沒有 staging：`v2` 合併就直接上線。目前只有作者自己使用，壞了再修的代價小，可以接受。

**現在就有感的缺口**：在手機上試 `v2` 的改動，只能先合併上線。

**預覽環境的做法**：網頁版的資料存在瀏覽器裡，而瀏覽器是依網址來源（origin）區分儲存空間的，所以預覽環境必須放在**另一個來源**，資料才不會和正式網站混在一起。
- 不要放在同一個 GitHub Pages 網站的子路徑（例如 `/RunningCoach/preview/`）：同一個來源共用 localStorage 與 OPFS，預覽版的 bug 或資料庫 migration 可能改到正式資料。同一個帳號底下的其他 Pages 網站也是同一個來源（KI-026）。
- 建議用 Cloudflare Pages：在 Cloudflare 的後台連結這個 repo，每個分支都會建置出自己的網址（`*.pages.dev`），不必在 repo 裡放任何金鑰。建置指令為 `npm ci && npm run build -w @running-coach/web`，輸出目錄為 `apps/web/dist`，Node 版本設為 22；網址在根路徑，不用改 `--base`。需要使用者建立 Cloudflare 帳號並授權 GitHub。
- 預覽網址是另一個來源，API key、設定與資料都要重新設定；可以搭配測試模式。
- Discord bot 的預覽需要另一個 bot token 與 VM 上的第二個容器，目前不做。

**對外前要補齊的**：訂閱、帳號與金流上線，也就是有其他使用者之後。
- staging：`v2` 自動部署到預覽網址；代理有自己的 staging（金流用測試模式的金鑰、獨立的帳號資料）；Discord 用另一個測試用的 bot。
- prod：只在發版時更新，例如打 tag 或從 `main` 手動觸發，並保留回退方式。
- 資料庫 migration 要先在 staging 以正式資料的副本驗證。網頁版的資料在使用者的裝置上，migration 一旦出錯就無法從伺服器修正，所以要更謹慎。

### 12.5 養成遊戲的相容層（2026-10-16，提案）

使用者問相容層有沒有建議的方向。12.3 列了原則，這裡是具體的切法，以及現在可以先做的部分。尚未決定（11 #14）。

**核心體驗**（2026-10-18 討論，先談核心，不談遊戲類型）

使用者的方向：有一定的社交性但不是重點，類似 Duolingo，可以滿足想贏的快感，但贏了不會怎樣、輸了也不怎樣。重點是看得見的累積：打開時有「原來我已經做了這麼多」的感覺。不強調進步，長時間休息也不會帶來壓力或任何負面的感受。

一句話：打開就看到自己累積了多少，休息不會失去任何東西。以下是對應的提案：

- **只增不減**：任何數值都不倒退。沒有血量、不會枯萎、沒有降級，也沒有「連續 N 天」。Duolingo 最主要的壓力來源就是連勝（甚至要買「連勝凍結」來保住它）。要計數就用只增不減的，例如「有運動的週數：37 週」，中斷了也不歸零。
- **休息回來**：畫面和離開時一模一樣，加上「歡迎回來」與一則回憶；回來後的第一次跑步給一個「回歸」的標記。獎勵回來，不記錄缺席。
- **按件數排列，不按日曆排列**：日曆式的呈現（GitHub 的方格、月曆打勾）會讓沒動的日子特別顯眼，休息一陣子就是一大片空白。改成每做一次就「放上一樣東西」，只有做過的才出現，沒有空位。東西的大小或種類依強度分鐘的級距，20 分鐘的慢跑也看得到新增。成長的門檻前密後疏，新手很快看到變化，累積多的人每次仍有新東西。
- **累積要具體**：每樣東西都點得開，看到那天的日期與教練當時的分析。打開時輪播一則回憶（「一年前的今天，你完成了第一次 10K」「你在雨天跑了 12 次」）。總量可以用生活化的比喻，例如累積的距離相當於從台北到哪裡；這只在自己的 App 裡顯示，所以可以用距離。
- **不呈現進步**：不放趨勢圖、百分比、和上週比較。個人最佳可以當回憶出現，不當主角。
- **輕度的每週比賽**：保留 Duolingo 聯賽「每週重新開始」的部分，這週輸了，下週大家又從零開始；拿掉降級、連勝與催促的推播（「你的朋友超越你了」）。比的是強度分鐘，每天有上限，新手和老手公平，也不會為了贏而過量。這週沒動的人不列為最後一名，只顯示「休息中」或不出現。贏了只有好看的標記（例如這週的皇冠），不影響任何數值。原本建議不做排行（見下方「和朋友的平台結合」），是擔心作弊與鼓勵比快；贏了沒有實質好處、又有每天上限，這兩個問題都小很多，所以可以做。
- **遊戲不主動找人**：不推播，只有打開時看得到。提醒是教練的事（教練動態），而教練的提醒是為了訓練。教練建議休息的那天，遊戲不能催人。

實作上要先處理的：
- 第一次打開的感受靠歷史資料。現在只同步最近 14 天，要加一次性的「匯入完整歷史」：只存紀錄，不產生 AI 分析，所以不花 LLM 的費用。
- 累積有了情感價值，資料只在一台裝置上就更怕遺失。遊戲是從紀錄重算的，換裝置時重新匯入 Intervals.icu 的歷史就能還原大部分（自評與跑後回報除外）；資料備份（11 #8）的優先度因此提高。
- 教練動態的「已經 N 天沒跑了」，休息越久數字越大，與「休息沒有壓力」不一致。建議超過兩週就不再顯示，改在回來跑步時說「歡迎回來」。

**架構：以資料契約連接，呈現先放在網頁版裡**（2026-10-18 討論）

使用者的想法：遊戲在程式碼上不和教練高度耦合，比較像教練開出提供資料的介面，任何人拿了教練的程式碼都能做自己想要的遊戲。呈現放在現有的網頁裡，或做成獨立的頁面或 App，在開發與使用體驗上各有優劣。

程式碼的切法：
- 介面是一份**資料契約**，不是函式庫的 API：版本化的進度事件（上方的格式 v1），以 JSON 交換。遊戲只依賴這份契約，不 import 核心。
- 分界：需要原始資料（心率、配速、體感）才算得出來的在核心算，放進事件，例如強度分鐘；只靠事件就能算的（經驗值、等級、收集、每週比賽）留給遊戲。
- 推導是純函式 `deriveProgressEvents(紀錄)`，不直接讀資料庫；核心另外提供讀資料庫的薄轉接層。測試模式的假資料、Discord 外殼、別人的遊戲都用同一個函式。
- 授權：核心是 AGPL。別人的遊戲只交換資料、不連結核心的程式碼時，一般認為不是衍生作品，不受 AGPL 約束。若希望別人能直接使用事件的型別定義或推導函式而不受限，可以把那個小套件另外以 MIT 授權。著作權人可以這樣做；收了外部貢獻之後就要先有貢獻者授權協議（第 8 節）。

呈現的位置：

| | 網頁版裡的一頁 | 同一個網站的獨立頁面 | 獨立的 App 或網站 |
|---|---|---|---|
| 取得資料 | 直接讀，不必傳送 | 同一個 OPFS，但同時只能有一個分頁開啟資料庫（6.1） | 要另外交接：匯出檔、開啟時傳遞（postMessage），或經伺服器 |
| 打開就看到累積 | 每次打開教練就在 | 要另外打開 | 要另外安裝、另外打開 |
| 視覺與效能 | 受現有版面限制；圖像資源大時要延遲載入 | 可以全螢幕、分開打包 | 完全自由，可以做原生 |
| 開發與部署 | 最簡單，測試模式直接可用 | 同一次部署，要處理分頁衝突 | 另一套建置、部署，可能還要帳號 |

建議：
- 程式碼一開始就分開（獨立的套件，只吃事件）；呈現先放在網頁版裡，做成延遲載入、可以全螢幕的一頁。資料就在旁邊，教練動態可以放一張「你已經累積了…」的小卡片當入口。
- 之後要拆成同網站的獨立頁面時，避開分頁衝突的做法：教練在資料變動後，把最新的進度事件寫成一份快照（例如存在 IndexedDB，可以多個分頁同時讀），遊戲只讀快照、不開資料庫。
- 獨立的 App 或朋友的平台：同一份事件以匯出或傳遞交給它們。資料在裝置上、沒有伺服器可以代送，所以由使用者觸發，例如開啟遊戲時傳遞，或主動分享。

**實作計畫：進度事件 v1 與匯入完整歷史**（2026-10-18，提案，尚未實作）

進度事件 v1：

```json
{ "v": 1, "id": "run:i123456", "type": "run_completed", "date": "2026-10-18", "rev": "a1b2c3",
  "attrs": { "minutes": 52, "intensity_minutes": 64, "effort": "moderate", "time_of_day": "morning", "longer_than_usual": false, "reported": true } }
```

| 類型 | 來源 | 屬性 |
|------|------|------|
| `run_completed` | 每一筆跑步 | `minutes`（移動時間）、`intensity_minutes`、`effort`（easy／moderate／hard，沒有資料時為 null）、`time_of_day`（清晨／白天／傍晚／夜間）、`longer_than_usual`（比自己最近 4 週的平均長）、`reported`（有沒有跑後回報） |
| `checkin` | 每天的自評 | 沒有屬性，只表示有回報；分數不送出 |
| `race_finished` | 已記錄成績的賽事 | `distance_class`（5K／10K／半馬／全馬／其他）；成績不送出 |

與上方草案的差別：
- `rev` 改為內容的雜湊：事件不存、每次重算，沒有地方記遞增的版本號；內容改變時雜湊跟著變，接收端依 `id` 覆蓋。
- 「補上體感」併入 `run_completed` 的 `reported`，不另設類型。
- 時長直接給分鐘數，不再分級：時長本身不敏感，強度分鐘也由它算出；敏感的是配速、距離與心率，這些不送出。
- `rest_day`、`plan_set` 先不做：休息日要從「沒跑」推導，正是核心體驗想避免的日曆思維；課表也還不是結構化的資料。課表結構化之後再加。
- 里程碑（第 100 次、第一場半馬）不是事件，由遊戲規則從事件算出。

強度分鐘，依可用的資料逐步退回：
1. Intervals.icu 活動資料中各心率區間的時間：Z4 以上的分鐘算 2 倍，其餘算 1 倍。欄位名稱要以真實帳號確認。
2. 只有平均心率：達到最大心率的 80% 以上，整段算 2 倍，否則 1 倍。最大心率用選手資料（實測，或 220－年齡）。
3. 沒有心率、有體感：體感 7 分以上算 2 倍。
4. 都沒有：1 倍。

跑步的每一分鐘至少算 1 倍，輕鬆跑不會「不算」。80% 的門檻接近美國運動醫學會以最大心率 77% 以上為高強度的分法，也對應現有的 Z4。

程式碼：
- 新套件 `packages/progress`：事件的型別與 `deriveProgressEvents(input)`。輸入是它自己定義的精簡格式（每筆跑步的日期、開始時間、分鐘數、心率、各區間的時間、體感；自評的日期；賽事的日期與距離），不依賴核心，之後可以單獨改用 MIT 授權。
- 核心加一層薄的轉接：從資料庫讀出紀錄，轉成輸入格式後呼叫推導（`Coach.progressEvents()`）。
- 測試：相同輸入每次產生相同的 `id` 與 `rev`；補填體感後 `rev` 改變、`id` 不變；各種資料缺漏時的退回；假資料產生器的各個情境。這一步沒有畫面。

匯入完整歷史：
- 設定頁的 Intervals.icu 區塊加上「匯入完整歷史」，說明只存紀錄、不產生 AI 分析（不花模型的費用），可能要一兩分鐘。
- 從今年往回，一次抓一年並顯示進度；連續兩年沒有跑步就停，也可以指定最早的年份。歷史匯入的請求放寬逾時（現在是 15 秒），太大就改成半年一次。
- 存法與測試模式存較早的假資料相同：直接存入，不產生分析，不合併等待同步的跑後回報。依 Intervals.icu 的活動 id 去重，可以重跑，中斷了再按一次即可。
- 之後的一般同步不變，最近 14 天照常產生分析。
- 舊紀錄沒有教練的分析，回憶只顯示數據；之後可以對單筆按「產生分析」。
- 只抓跑步，與一般同步相同；要跨項目時再一起放寬。
- 每筆存完整的原始資料（開始時間、各區間的時間都在其中），約幾 KB；一千筆約數 MB，匯出檔也會跟著變大。
- 據搜尋所知，Intervals.icu 因為 Strava 的 API 條款，不透過 API 提供從 Strava 匯入的活動；較早的紀錄若經由 Strava 進入 Intervals.icu，就抓不到。要以真實帳號確認。
- 對教練的影響：跑量暴增的判斷要比較前三週，新使用者只同步了 14 天，平均其實少算；匯入歷史後才準確。工具只查最近幾天、系統提示不帶全部紀錄，所以不會讓每次對話變貴。

**分成三層，現在只需要做第一層**
1. 進度事件（核心）：由本機的紀錄推導出的抽象事件。這是唯一對外的介面，遊戲與社交平台只看得到這一層。
2. 規則（遊戲）：把事件換算成經驗值、等級、任務與收集。規則是事件的純函式，帶版本號；可以放在 App 裡，也可以放在朋友的平台上。
3. 呈現：RPG 的角色、Pikmin 式的花園，或朋友平台上的頭像。同一份進度可以有不同的呈現。

規則與畫面可以一直改，甚至整個換掉，不會失去已累積的進度；朋友的平台只要接事件，不必懂跑步。

**事件即時推導，不另外存**：事件是本機紀錄（訓練、自評、賽事、課表）的純函式，和教練動態一樣即時算出。補填體感、修改紀錄或修正推導方式之後，重算的結果自然一致。只需要記錄「送出去過哪些事件、哪一版」，用來補送或撤回。

**事件格式 v1（草案）**

```json
{ "v": 1, "id": "run:i12345", "type": "run_completed", "date": "2026-10-16", "rev": 2, "attrs": { "duration": "30-60", "effort": "easy", "longer_than_usual": false, "time_of_day": "morning" } }
```

- `id` 由來源紀錄穩定產生：訓練用 Intervals.icu 的活動 id，自評用日期，賽事用賽事 id。重算不會重複計分。內容改了（例如補填體感）時 `rev` 加一，接收端依 `id` 覆蓋，和 12.3 跨裝置同步的「後寫入者為準」相同。
- 類型：`run_completed`、`run_reported`（補上體感）、`checkin`、`rest_day`（當天沒跑，而且課表是休息或自評狀況差）、`race_finished`、`plan_set`（排了本週課表）。課表結構化（12.1 第 2 項）之後再加 `planned_session_completed`。
- 屬性只用分級：
  - 時長：30 分鐘以下、30–60、60–90、90 分鐘以上。
  - 強度：輕鬆、中等、吃力。依體感；沒有體感時，依平均心率占最大心率的比例。
  - 比平常長：和自己最近 4 週的平均比，不用絕對距離。新手和老手用同一套分級，社交上比較公平，也不會透露實力。
  - 時段：清晨、白天、傍晚、夜間，給收集要素用。不帶時間戳。
  - 聽身體的話：教練動態建議降低強度的那天，跑了輕鬆跑或休息。
- 不帶：距離、配速、心率、HRV、睡眠、位置、路線、天氣與任何備註文字。

**基礎數值：用強度分鐘，不用卡路里**（2026-10-18 討論）

使用者問：能不能用卡路里當遊戲的基礎數值，作為不同強度、不同項目共通的單位，也降低對外提供資料的敏感性。資料是有的：每筆跑步都已讀取 Intervals.icu 的 `calories`（來自手錶）與 Intervals.icu 算的訓練負荷（`icu_training_load`，存為 `training_load`）。但卡路里不適合當基礎數值：

- 會透露體重：跑步每公里大約消耗「體重公斤數」大卡，卡路里除以距離（即使只有時長的分級）就能估出體重。這和降低敏感性的目的相反。
- 不公平：同一趟跑步，體重越重卡路里越高；各家手錶的算法也不同，朋友之間無法比較。
- 不準：史丹佛大學 2017 年測了 7 款穿戴裝置，心率大多準確，熱量估計沒有一款達到可接受的誤差。
- 鼓勵量，而且容易聯想到減重與飲食控制。

共通的單位改用「強度分鐘」：時長乘上相對強度的倍數（中等 1 倍、高強度 2 倍；輕鬆的部分另外計算或給較低的倍數），強度依自己的心率區間或體感判斷，不用配速。這和世界衛生組織每週 150 分鐘中等強度（或 75 分鐘高強度）的建議、Garmin 的 Intensity Minutes 是同一個概念，所以容易解釋。
- 跨項目通用，不受體重與實力影響，對外只有分鐘數。
- 訓練負荷也和個人的閾值相對、跨項目，可以在規則內部用來微調；但它取決於 Intervals.icu 上的閾值設定，可能沒有值，使用者也比較難理解，所以不當主要的單位。
- 卡路里只在 App 裡給使用者自己看，不送出去，也不換算成分數。
- 一樣要有每天、每週的上限，避免鼓勵過量（見下方的規則建議）。
- 目前只同步跑步。要跨項目，同步就要納入其他類型（騎車、游泳、肌力訓練），教練也會看到這些紀錄；屆時再決定。

**規則的建議**（給遊戲設計，不在核心）
- 經驗值主要來自持續：完成、回報、照計畫休息。同一天多跑不多拿（每天有上限），以免鼓勵過量、和教練的建議衝突。
- 連續紀錄用「每週完成幾次」，不用「每天不間斷」；休息日不會中斷連續紀錄。
- 自評很差或長時間沒跑時進入「養傷」狀態，任務改成回報狀況、伸展；不倒扣。
- 遊戲和教練要說同一件事：教練建議休息的那天，休息就是當天最好的選擇，遊戲也要給獎勵。

**和朋友的平台結合**
- 以合作為主，不做排行：例如大家一起養一棵樹、一起打一個 boss。事件來自使用者的裝置，改 App 就能偽造，排行榜擋不住作弊；合作玩法作弊的動機低，也不會把跑者推向比快。（2026-10-18 修正：贏了沒有實質好處、又有每天上限時，可以有輕度的每週比賽，見上方的「核心體驗」。）
- 傳送：網頁版的資料只在裝置上，沒有伺服器可以代送，所以由 App 在打開時把新的或改過的事件送到對方的 API。使用者可以選擇分享哪些類型，隨時停止並要求對方刪除。
- 要先問朋友：能不能接收這種事件（API 或 webhook）、帳號怎麼連結、平台上是否已有成長系統可以直接對應。

**建議的順序**
1. 核心加上 `deriveProgressEvents()` 與單元測試。測試模式的假資料可以直接看過度訓練、受傷、減量等情境會產生哪些事件。不做畫面。
2. App 裡做最簡單的呈現（等級與最近的事件），自己用一陣子，調整規則。
3. 拿事件格式和朋友討論介面。
4. 課表結構化之後，補上「照課表完成」。

### 12.6 第三輪討論（2026-10-19）

**只有 iPhone 的使用者，怎麼把資料送進 Intervals.icu**

瀏覽器無法讀取 Apple「健康」的資料（HealthKit 沒有網頁的介面），所以在有原生 App 之前，要靠其他 iPhone App 把運動上傳到 Intervals.icu，網頁版再從 Intervals.icu 讀取。以下來自搜尋到的 App Store 頁面與 Intervals.icu 論壇，實作前要在本機確認。
- **經 Strava 不行**：Intervals.icu 因為 Strava 的 API 條款，不透過 API 提供從 Strava 匯入的活動，回傳的是「STRAVA activities are not available via the API」的說明。用 Strava App 記錄、再讓 Intervals.icu 從 Strava 抓的人，網頁版看不到這些跑步。
- **Intervals.icu Companion**（第三方，免費、有內購）：自動把 Apple Watch 或 iPhone 記錄的運動同步到 Intervals.icu，也同步 HRV、睡眠等每日資料，所以恢復資料（6.7）也用得上。開發者在論壇說過無法批次同步過去的運動。
- **HealthFit**（第三方）：可以把運動匯出到 Intervals.icu；也能把過去的運動批次匯出成 FIT 檔，再到 Intervals.icu 的網站批次匯入，用來補歷史。
- 這兩條路上傳的是 App 自己的檔案，不是 Strava 的資料，預期 API 讀得到，但要實測。
- 不經 Intervals.icu 的退路：網頁版提供手動新增一筆，或讀取 FIT／GPX 檔。缺點是沒有 Intervals.icu 算好的訓練負荷與恢復資料。
- 長期：iOS App 直接讀 HealthKit（6.4），iPhone 使用者就不需要 Intervals.icu。

**讓大家上架自己的遊戲或應用（使用者的構想）**

使用者的想法：與其自己做所有遊戲，不如做成一個平台，大家（包括我們）都可以上架自己的遊戲或應用；使用者比我們更了解使用者要什麼，也可能是比較可行的商業模式，至少收支打平。

技術上和 12.5 的資料契約一致：
- 小程式放在另一個來源的 iframe（sandbox）裡執行，只透過 postMessage 拿到進度事件，碰不到 API key 與資料庫；每個小程式第一次使用時，由使用者同意它可以拿哪些事件。
- 內容安全政策（6.1）要加上允許的 iframe 來源。

但以現在的規模，平台還不划算：
- 平台是雙邊市場：使用者少，開發者不會來；開發者少，使用者也不會為了平台而來。多數成功的平台是先有一個好用的產品，再開放給別人。
- 上架就要審核（惡意程式、詐騙、不當內容）、下架與客服，這些是固定成本，在有抽成收入之前就要先付。
- 之後若上架原生 App，App Store 對 App 內的小程式有專門的審查準則，數位商品要走 Apple 的內購。
- 大多數使用者不會自己做；但跑者裡寫程式的人不少（Intervals.icu 的社群就是例子），少數人做、多數人用。

建議分階段，先讓這件事「可以發生」，但不先建商店：
1. 現在：公開事件格式與範例，我們自己的遊戲當作第一個參考實作；朋友的社交平台是第一個外部的使用者。使用者可以用網址自行加入小程式，風險自負，沒有商店、沒有審核。
2. 真的有人做出東西：維護一份精選清單，由我們挑選、簡單檢查。
3. 有足夠的使用者之後：再考慮商店與抽成。

收支打平的來源：
- 現在的成本很低：使用者自備 LLM 的 key，網頁版放在免費的 GitHub Pages，只有作者自己的 VM。成本會出現在訂閱模式，由我們付 LLM 的費用。
- 所以主要的收入應該是訂閱（不必自備 key 的方便，5.4），定價要高於平均每人的 LLM 費用。
- 其他可以搭配的：我們自己的遊戲賣外觀類的道具（不影響數值，符合「贏了也不怎樣」）；開源專案的贊助；跑團或教練的團體方案（可以和朋友的平台一起談）。
- 不建議：裝備推薦的分潤連結。教練推薦裝備時有分潤，會讓人懷疑建議是否中立；真的要做必須明確揭露。
